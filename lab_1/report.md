# Лабораторная работа №1. Проектирование и создание структуры базы данных

**Тема:** Сервис аренды специализированного оборудования  
**СУБД:** PostgreSQL 16  
**Схема:** `public`, 15 таблиц, 3НФ

---

## 1. Анализ предметной области и бизнес-правила

Предметная область — сервис, сдающий в аренду специализированное оборудование (строительное, фото/видео, лабораторное). Клиенты бронируют единицы оборудования на период, оформляют заказы, оплачивают, получают доставку. Оборудование имеет иерархию категорий, справочник моделей, тарифы, журнал ТО и акты повреждений.

**Бизнес-правила:**

1. Пользователь может быть клиентом-арендатором (`customer`), сотрудником (`employee`) или администратором (`admin`). Один пользователь — не более одной записи клиента (1:1).
2. Каждая единица оборудования относится ровно к одной модели; модель — к одной категории. Категории образуют дерево (самоссылка `parent_id`), корневые категории имеют `parent_id IS NULL`.
3. Инвентарный номер единицы оборудования уникален в масштабе системы (`UNIQUE`).
4. Заказ на аренду принадлежит одному клиенту и содержит хотя бы одну позицию. Позиция связывает заказ и конкретную единицу оборудования (M:N), фиксируя тариф и цену на момент оформления.
5. Конец аренды не может быть раньше начала (`CHECK rental_end >= rental_start`).
6. Один заказ может иметь несколько платежей (частичная оплата, возвраты). Платёж не может быть на сумму ≤ 0.
7. Акт повреждения может быть привязан к заказу, но сохраняется даже при удалении заказа (`ON DELETE SET NULL`).
8. Один пользователь может оставить не более одного отзыва об одной единице оборудования (`UNIQUE (user_id, equipment_id)`), оценка — от 1 до 5.

## 2. ER-диаграмма

![ER-диаграмма БД аренды оборудования](docs/erd.png)

*Рисунок 1 — ER-диаграмма (15 сущностей, M:N через `rental_order_items`, иерархия `equipment_categories.parent_id`).*

**Ключевые связи:**
- **M:N:** `rental_orders ↔ equipment` через `rental_order_items` (составной PK `order_id, equipment_id`).
- **Иерархия:** `equipment_categories.parent_id → equipment_categories.id`.
- **1:1:** `users ↔ customers` (PK=FK), `equipment ↔ stock` (PK=FK).
- **1:N:** `customers → rental_orders`, `equipment_models → equipment`, `rental_orders → payments`, `equipment → maintenance_records`.

## 3. Нормализация: пример аномалии и её устранение

**Исходная «плоская» таблица (до нормализации):**

| order_id | customer_email | customer_name | equipment_inv | model_brand | model_name | category_name | tariff_price | rental_start | rental_end |
|---|---|---|---|---|---|---|---|---|---|
| 1 | ivan@mail.ru | Иван | INV-001 | Bosch | GBH 2-26 | Перфораторы | 500.00 | 2026-01-10 | 2026-01-15 |
| 1 | ivan@mail.ru | Иван | INV-002 | Makita | HR2470 | Перфораторы | 450.00 | 2026-01-10 | 2026-01-15 |
| 2 | ivan@mail.ru | Иван | INV-003 | Bosch | GWS 750 | Болгарки | 300.00 | 2026-02-01 | 2026-02-03 |

**Аномалии до нормализации:**

- **Вставки:** нельзя добавить новую модель оборудования, пока на неё нет заказа.
- **Обновления:** при смене email клиента нужно править все его строки; пропуск одной строки → рассогласование.
- **Удаления:** удалив последний заказ клиента, теряем сведения о клиенте; удалив заказ — теряем сведения о модели/категории.

**Устранение:**

- **1НФ:** все значения атомарны (нет списков в ячейках).
- **2НФ:** атрибуты, зависящие от части составного ключа `(order_id, equipment_id)`, вынесены: `model_brand`, `model_name` → `equipment_models`; `equipment_inv` → `equipment`.
- **3НФ:** транзитивные зависимости устранены: `customer_email`, `customer_name` → `users`/`customers`; `category_name` → `equipment_categories`; `tariff_price` → `tariffs`.

Результат — схема из 15 таблиц в 3НФ (см. `schema.sql`).

## 4. Обоснование выбора ключей

| Таблица | PK | Тип | Обоснование |
|---|---|---|---|
| `users` | `id` | Суррогатный (IDENTITY) | Стабильность; email — UNIQUE, но может измениться |
| `customers` | `user_id` | Естественный (FK) | Реализация 1:1; клиент не существует без пользователя |
| `equipment_categories` | `id` | Суррогатный | Иерархия; name UNIQUE, но переименование возможно |
| `equipment_models` | `id` | Суррогатный | UNIQUE `(brand, model_name)` — естественный ключ-кандидат |
| `equipment` | `id` | Суррогатный | `inventory_number` UNIQUE — естественный ключ, но PK на суррогате стабильнее |
| `stock` | `equipment_id` | Естественный (FK) | Реализация 1:1 |
| `tariffs` | `id` | Суррогатный | Историчность (`valid_from`/`valid_to`) — версии тарифа |
| `rental_orders` | `id` | Суррогатный | Стандарт для транзакционных сущностей |
| `rental_order_items` | `(order_id, equipment_id)` | Составной | M:N; одна единица в заказе один раз |
| `payments` | `id` | Суррогатный | Несколько платежей на заказ |
| `maintenance_records` | `id` | Суррогатный | История ТО |
| `damage_reports` | `id` | Суррогатный | Акт повреждения |
| `addresses` | `id` | Суррогатный | У клиента может быть много адресов |
| `deliveries` | `id` | Суррогатный | `order_id` UNIQUE — 1:1 с заказом |
| `reviews` | `id` | Суррогатный | UNIQUE `(user_id, equipment_id)` — естественный ключ-кандидат |

**Правила `ON DELETE`:**

| FK | Правило | Почему |
|---|---|---|
| `rental_order_items.order_id → rental_orders` | `CASCADE` | Удалили заказ — позиции не нужны |
| `rental_order_items.equipment_id → equipment` | `RESTRICT` | Нельзя удалить оборудование из оформленного заказа |
| `damage_reports.order_id → rental_orders` | `SET NULL` | Акт повреждения сохраняется для истории |
| `customers.user_id → users` | `CASCADE` | Клиент не существует без пользователя |
| `stock.equipment_id → equipment` | `CASCADE` | Остаток не существует без единицы |

## 6. Вывод

Спроектирована схема БД сервиса аренды оборудования в 3НФ (15 таблиц). Обеспечены: ссылочная целостность (FK с осмысленными `ON DELETE`), доменная целостность (`CHECK`, `UNIQUE`, `NOT NULL`), поддержка M:N, иерархии и JSONB для гибких атрибутов. Схема реализована в PostgreSQL 16 и воспроизводится единым DDL-скриптом (`schema.sql`) через Docker (`docker compose up -d` после `make sync`).
